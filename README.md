# دستیار پژوهشی هوشمند 🤖📚

پروژه‌ی آموزشی و کوچک برای یادگیری **Function Calling** و **Tool Calling** با Python و مدل‌های سازگار با OpenAI.

موضوع پژوهش را در یک صفحه چت ساده وارد می‌کنی؛ مدل هوش مصنوعی خودش تصمیم می‌گیرد که برای جمع‌آوری اطلاعات به ابزار
جست‌وجوی اینترنت (`search_web`) نیاز دارد یا نه، بک‌اند پایتون آن ابزار را واقعاً اجرا می‌کند، نتیجه به مدل برمی‌گردد و
در پایان یک مقاله فارسی در فایل Markdown ذخیره می‌شود.

> هدف این پروژه فقط **یادگیری** است: بدون دیتابیس، بدون فریم‌ورک فرانت‌اند، بدون معماری پیچیده.

---

## ۱) این برنامه چه کاری انجام می‌دهد؟

۱. موضوع پژوهش را از کاربر می‌گیرد.
۲. تعریف ابزار `search_web` را در قالب JSON Schema به مدل معرفی می‌کند.
۳. مدل در صورت نیاز، درخواست فراخوانی ابزار (`tool_calls`) به‌همراه آرگومان‌ها برمی‌گرداند.
۴. بک‌اند آرگومان‌ها را می‌خواند و **تابع واقعی پایتون** را اجرا می‌کند (جست‌وجوی واقعی اینترنت).
۵. نتیجه ابزار با نقش `tool` و همان `tool_call_id` به مدل برگردانده می‌شود؛ پیش از آن، نتایج با **Compaction «پنجره لغزان»** فشرده می‌شوند تا Context کوچک بماند.
۶. مدل مقاله فارسی (عنوان، مقدمه، بخش‌ها، جمع‌بندی، منابع) را می‌نویسد.
۷. مقاله با UTF-8 در پوشه `research_notes` ذخیره و مسیر فایل به کاربر نمایش داده می‌شود.

## ۳) تفاوت Function Calling و Tool Calling

- **Function Calling:** مدل درخواست می‌کند یک *تابع مشخص* با *آرگومان‌های مشخص* اجرا شود. این اصطلاح معمولاً برای
  قابلیت فراخوانی تابع در API مدل استفاده می‌شود (همان `tools` و `tool_calls`).
- **Tool Calling:** اصطلاح گسترده‌تر و رایج‌تر برای «درخواست استفاده از ابزار». ابزار می‌تواند یک تابع باشد یا هر چیز
  دیگری (جست‌وجو، ماشین‌حساب، خواندن فایل، …).

در این پروژه هر دو اصطلاح به یک چیز اشاره دارند: مدل درخواست اجرای تابع `search_web` را می‌دهد و **خودش آن را اجرا
نمی‌کند**؛ اجرای واقعی کار بک‌اند است. در بعضی APIها این دو اصطلاح به‌جای یکدیگر یا با تفاوت‌های جزئی به کار می‌روند.

## ۶) تنظیمات فایل `.env`

فایل `.env` را در پوشه‌ی پروژه بساز (از روی `.env.example`) و مقادیر را داخل آن بگذار. **هیچ کلیدی در کد پایتون یا
JavaScript نوشته نشده است.**

| متغیر | توضیح | پیش‌فرض |
|---|---|---|
| `OPENAI_API_KEY` | کلید API مدل (ضروری) | — |
| `OPENAI_BASE_URL` | آدرس پایه سرویس سازگار با OpenAI | بدون مقدار = سرویس رسمی OpenAI |
| `OPENAI_MODEL` | نام مدل (باید از tool calling پشتیبانی کند) | `gpt-4o-mini` |
| `OPENAI_CONNECT_TIMEOUT` | مهلت برقراری اتصال با مدل (ثانیه) | `30` |
| `OPENAI_READ_TIMEOUT` | مهلت انتظار برای پاسخ مدل (ثانیه) | `300` |
| `OPENAI_MAX_RETRIES` | تعداد تلاش مجدد در خطای موقت شبکه | `2` |
| `SEARCH_PROVIDER` | سرویس جست‌وجو: `wikipedia` یا `tavily` | `wikipedia` |
| `SEARCH_API_KEY` | کلید Tavily (فقط برای `tavily`) | خالی |
| `SEARCH_MAX_RESULTS` | بیشترین تعداد نتایج جست‌وجو | `5` |
| `SEARCH_TIMEOUT` | مهلت تماس با سرویس جست‌وجو (ثانیه) | `25` |
| `RESEARCH_NOTES_DIR` | پوشه ذخیره مقاله‌ها | `research_notes` |
| `COMPACTION_STRATEGY` | راهبرد فشرده‌سازی Context: `sliding` (پنجره لغزان) یا `truncate` | `sliding` |
| `COMPACTION_WINDOW` | اندازه پنجره: چند نتیجه در Context بماند | `3` |
| `COMPACTION_SNIPPET_LIMIT` | بیشترین نویسه «خلاصه» هر نتیجه | `250` |
| `COMPACTION_MAX_CHARS` | سقف نویسه مجموع نتایج هر پیام tool (پنجره تا رعایت آن می‌لغزد) | `1500` |
| `COMPACTION_HISTORY_MAX_CHARS` | سقف نویسه تاریخچه مکالمه («پنجره لغزان» روی پیام‌ها) | `8000` |
| `COMPACTION_HISTORY_MIN_MESSAGES` | کمترین شمار پیام‌های آخر که در هر حالت می‌مانند | `4` |

نکته‌ها:

- `load_dotenv()` فایل `.env` را از پوشه‌ی همین پروژه و اگر نبود از **پوشه‌های بالاتر** هم می‌خواند؛ پس اگر `.env`
  در پوشه‌ی والدِ `dastyar` باشد هم خوانده می‌شود.
- فایل `.env` در `.gitignore` است و به گیت نمی‌رود.
- اگر سرویس مدل شما از `base_url` سفارشی پشتیبانی نمی‌کند، `OPENAI_BASE_URL` را خالی بگذار تا کلاینت از آدرس
  پیش‌فرض OpenAI استفاده کند. (این رفتار به خود سرویس بستگی دارد.)
- مدل‌های ضعیف‌تر ممکن است `tools` را پشتیبانی نکنند؛ در آن صورت مدل هیچ `tool_calls` برنمی‌گرداند و برنامه بدون
  جست‌وجو مقاله می‌نویسد (این حالت در رابط کاربری با برچسب «رد شد» نمایش داده می‌شود).

### فشرده‌سازی Context با «پنجره لغزان» (Compaction)

پیش از فرستادن نتایج جست‌وجو به مدل، Context کوچک می‌شود. راهبرد پیش‌فرض **پنجره لغزان (Sliding Window)** است و دو بخش دارد:

۱. **پنجره روی تازه‌ترین نتایج می‌نشیند**: `results[-window:]` — یعنی به‌جای همیشه «N نتیجه‌ی اول»، تازه‌ترین نتایج نگه داشته می‌شوند.
۲. **لغزش پنجره با سقف نویسه**: اگر مجموع نویسه‌های داخل پنجره از `COMPACTION_MAX_CHARS` بگذرد، پنجره یک قدم می‌لغزد و قدیمی‌ترین نتیجه‌ی داخل پنجره بیرون می‌افتد (تا دست‌کم یک نتیجه بماند).

خود تاریخچه‌ی مکالمه هم با «پنجره لغزان» جمع می‌شود (`compact_messages_sliding`):

- پیام `system` همیشه می‌ماند و پنجره از انتهای تاریخچه (تازه‌ترین پیام‌ها) عقب می‌رود تا `COMPACTION_HISTORY_MAX_CHARS` رعایت شود.
- کمترین شمار پیام‌های آخر (`COMPACTION_HISTORY_MIN_MESSAGES`) در هر حالت حفظ می‌شود.
- اگر ابتدای پنجره روی پیام `tool` بیفتد، پنجره یک قدم عقب‌تر می‌رود تا پیام `assistant` صاحب همان `tool_calls` هم داخل پنجره بماند؛ وگرنه درخواست به مدل **نامعتبر** می‌شود (خطای API).

با `COMPACTION_STRATEGY=truncate` رفتار ساده‌ی قبلی برمی‌گردد (فقط N نتیجه‌ی اول می‌ماند). تنظیمات واقعی هر لحظه در `GET /api/health` زیر کلید `compaction` دیده می‌شود.

## ۷) سرویس جست‌وجو: چرا و کدام؟

جست‌وجو **واقعی** است و هیچ نتیجه‌ی ساختگی در کد وجود ندارد. دو گزینه در پروژه پیاده شده است:

| مقدار `SEARCH_PROVIDER` | سرویس | نیاز به کلید؟ | چه چیزی برمی‌گرداند |
|---|---|---|---|
| `wikipedia` (پیش‌فرض) | MediaWiki API ویکی‌پدیای فارسی | ❌ بدون کلید | عنوان، لینک واقعی و خلاصه |
| `tavily` | Tavily Search API | ✅ `SEARCH_API_KEY` | عنوان، لینک و متن خلاصه از کل وب |

**گزینه ۱ — ویکی‌پدیا (پیش‌فرض، بدون کلید):** دلیل انتخاب این است که بدون کلید کار می‌کند و در همین محیط پاسخ
واقعی ✅ داد. (DuckDuckGo و چند نمونه SearxNG به‌خاطر محدودیت ضدربات پاسخ ندادند.) محدودیتش این است که منابع فقط از
ویکی‌پدیای فارسی می‌آید، نه از کل وب.

**گزینه ۲ — Tavily (جست‌وجوی عمومی وب، نیازمند کلید):**

۱. در <https://tavily.com> ثبت‌نام کن و کلید رایگان بگیر.
۲. در `.env` بگذار:

```
SEARCH_PROVIDER=tavily
SEARCH_API_KEY=tvly-xxxxxxxxxxxxxxxxxxxx
```

اگر `SEARCH_PROVIDER=tavily` باشد ولی `SEARCH_API_KEY` خالی باشد، برنامه **خطای واضح** می‌دهد و هیچ نتیجه‌ی
ساختگی جای آن را نمی‌گیرد. همین رفتار برای خطای شبکه هم برقرار است.

## ۱۰) نقشه کد: قطعه‌های اصلی Function Calling و Tool Calling کجاست؟

همه‌ی این قطعه‌ها در `main.py` هستند (شماره خط‌ها بر اساس نسخه فعلی فایل):

| پرسش | جای دقیق کد |
|---|---|
| **تعریف ابزار کجاست؟** | خط **159**: `SEARCH_WEB_TOOL` — یک JSON Schema با `name`، `description` و `parameters` |
| **مدل چطور ابزار را می‌بیند؟** | خط **650**: `tools=[SEARCH_WEB_TOOL]` و `tool_choice="auto"` داخل `_ask_model` |
| **مدل چطور تصمیم به فراخوانی ابزار می‌گیرد؟** | خط **685**: پاسخ مدل گرفته می‌شود و `model_message.tool_calls` خوانده می‌شود |
| **آرگومان‌های ابزار کجا خوانده می‌شوند؟** | خط **343**: `_parse_tool_arguments` و استخراج `query` |
| **تابع پایتون کجا اجرا می‌شود؟** | خط **709**: `asyncio.to_thread(search_web, query)` |
| **Compaction «پنجره لغزان» کجاست؟** | خط **371**: `compact_search_results` (پنجره روی نتایج) و خط **448**: `compact_messages_sliding` (پنجره روی تاریخچه) |
| **فشرده‌سازی کجا در جریان کار صدا زده می‌شود؟** | خط **717**: نتایج جست‌وجو و خط **740**: تاریخچه‌ی مکالمه، پیش از فراخوانی نهایی مدل |
| **نتیجه ابزار چطور به مدل برمی‌گردد؟** | خط **728**: پیام با `role="tool"` و همان `tool_call_id` |
| **پاسخ نهایی (مقاله) چطور تولید می‌شود؟** | خط **749**: فراخوانی مدل با تاریخچه‌ی پنجره‌شده |
| **ذخیره فایل Markdown کجاست؟** | خط **536**: `save_article` و خط **560**: `write_text(..., encoding="utf-8")` |
| **مراحل چطور زنده به مرورگر می‌رسند؟** | `run_research` (خط 660) رویدادها را `yield` می‌کند، `/api/research/stream` (خط 873) آنها را با SSE می‌فرستد و `static/script.js` نمایش می‌دهد |

جان ماجرا (خلاصه‌ی جریان در شش خط مهم):

```python
# ۱) مدل با معرفی ابزار صدا زده می‌شود   →  main.py:650
# ۲) مدل درخواست اجرای ابزار می‌دهد      →  main.py:685   tool_calls = list(model_message.tool_calls or [])
# ۳) بک‌اند تابع واقعی را اجرا می‌کند      →  main.py:709   results = await asyncio.to_thread(search_web, query)
# ۴) نتایج با «پنجره لغزان» فشرده می‌شوند →  main.py:717   compact_results = compact_search_results(results)
# ۵) تاریخچه هم با پنجره لغزان جمع می‌شود  →  main.py:740   messages = compact_messages_sliding(messages)
# ۶) نتیجه با نقش tool برمی‌گردد          →  main.py:728   {"role": "tool", "tool_call_id": call.id, ...}
```

نکته‌ی کلیدی آموزشی: مدل فقط `tool_calls` (نام ابزار + آرگومان‌ها) تولید می‌کند؛ **هیچ کدی از سمت مدل اجرا نمی‌شود** و
اجرای واقعی تابع `search_web` کاملاً وظیفه‌ی بک‌اند پایتون است.

| وضعیت | رفتار برنامه |
|---|---|
| موضوع خالی | خطای فارسی روشن؛ در SSE رویداد `error`، در `POST` پاسخ `400` |

| تصمیم مدل به فراخوانی ابزار | ✅ `finish_reason=tool_calls` با آرگومان `{"query":"کاربرد هوش مصنوعی در پزشکی"}` |
| جست‌وجوی واقعی (`search_web` در تنها) | ✅ ۵ نتیجه با عنوان، لینک و خلاصه از ویکی‌پدیا |
| موضوع خالی | ✅ خطای واضح: «موضوع پژوهش خالی است. یک موضوع واقعی وارد کن.» |
| صفحه فرانت‌اند (`GET /`) | ✅ کد ۲۰۰ و همه بخش‌های UI (عنوان، ورودی، دکمه‌ها، بخش مراحل) |
| فایل‌های استاتیک | ✅ `style.css` و `script.js` با کد ۲۰۰ |
| `GET /api/health` و `GET /docs` | ✅ هر دو کد ۲۰۰ (کلیدها افشا نمی‌شوند) |
| `POST /api/research` با موضوع فارسی | ✅ کد ۲۰۰ در ۱۶٫۴ ثانیه، ۵ منبع، `file_path` واقعی و فایل ۵۶۶۰ بایتی روی دیسک |
| `POST /api/research` با موضوع خالی | ✅ کد ۴۰۰ با پیام فارسی روشن |
| جریان زنده مراحل (SSE) | ✅ ۸۴۷۸ بایت در ۱۶٫۳ ثانیه با ترتیب: `topic:running → topic:done → decide:running → decide:done → search:running → search:done → send:done → article:running → article:done → save:running → save:done → done` |
| Compaction «پنجره لغزان» (۲۱ بررسی خودکار) | ✅ همه PASS: نگه‌داشتن تازه‌ترین نتایج، لغزش پنجره با سقف نویسه، ماندن دست‌کم یک نتیجه، برش عنوان/خلاصه، دست‌نخورده‌بودن ورودی، راهبرد `truncate` |
| «پنجره لغزان» تاریخچه‌ی مکالمه | ✅ برای ۷۸ سقف نویسه‌ی مختلف: پیام `system` حفظ شد، هر پیام `tool` با `assistant` صاحبش ماند، ترتیب تغییر نکرد و دست‌کم پیام‌های آخر باقی ماندند |
| تنظیمات فشرده‌سازی در `GET /api/health` | ✅ `{"strategy":"sliding","window":3,"snippet_limit":250,"max_chars":1500,"history_max_chars":8000,"history_min_messages":4}` |
| اجرای زنده‌ی end-to-end پس از تغییر (سرویس `tokenharbor`، مدل `deepseek-v4.1-flash:free`، جست‌وجو `wikipedia`) | ✅ `used_tool=True`، ۴ فراخوانی ابزار، ۱۵ منبع واقعی، در هر فراخوانی ۵ نتیجه → ۳ نتیجه با پنجره لغزان (۹۷۲ تا ۱۱۳۹ نویسه)، مقاله ۵۹۳۲ نویسه‌ای ذخیره شد |
| مسیرهای خطا پس از تغییر | ✅ موضوع خالی → کد `400` و رویداد `error` در SSE؛ صفحه `/` کد `200` |
| سقف پیش‌فرض تاریخچه (۸۰۰۰ نویسه) در اجرای زنده | ⚪ پر نشد؛ پس «بیرون افتادن پیام‌های قدیمی از تاریخچه» فقط در تست خودکار با ۷۸ سقف کوچک سنجیده شد، نه در اجرای زنده |

دو نمونه از مقاله‌های تولیدشده در همین تست داخل پوشه‌ی `research_notes` باقی مانده است:
`research-20261028-151705.md` (مسیر `POST`) و `research-20261028-151721.md` (مسیر SSE).

### چه چیزی آزمایش **نشد** (صادقانه)

- **مسیر `SEARCH_PROVIDER=tavily`:** کلید Tavily در دسترس نبود. فقط بررسی شد که سرویس بدون کلید معتبر پاسخ `401`
  می‌دهد و کد ما در آن حالت پیام خطای روشن می‌دهد (نه نتیجه‌ی ساختگی). این مسیر به‌صورت کامل end-to-end تست نشده است.
- **خطای شبیه‌سازی‌شده‌ی قطع اینترنت یا مهلت زمانی جست‌وجو:** کد مسیر خطا دارد، ولی شبکه در تست برقرار بود و این مسیر
  عملاً رخ نداد.
- **کلیک دستی روی رابط کاربری در مرورگر:** انجام نشد؛ فقط سروشدن صفحه/فایل‌ها و خروجی واقعی SSE بررسی شد. کد
  `static/script.js` همان قالب رویدادهای SSE را با `fetch` می‌خواند.
- **DuckDuckGo به‌عنوان سرویس جست‌وجو:** در این محیط کار نکرد (پاسخ `202` و صفحه‌ی چالش ضدربات)، پس در پروژه
  استفاده نشده است.

## ۱۳) محدودیت‌ها و قدم‌های بعدی

محدودیت‌های عمدی برای سادگی آموزشی:

- بدون دیتابیس، بدون ورود/احراز هویت، بدون صف کار، بدون Docker، بدون فریم‌ورک فرانت‌اند.
- پژوهش هم‌زمان (سینکرون) است؛ برای موضوع‌های سنگین چند ده ثانیه طول می‌کشد.
- فقط یک ابزار (`search_web`).
- در حالت عادی فقط **یک دور** فراخوانی ابزار انجام می‌شود (چند درخواست در همان یک دور پشتیبانی می‌شود).
- مقاله فقط روی دیسک محلی در پوشه `research_notes` ذخیره می‌شود.

قدم‌های بعدی برای یادگیری:

۱. یک ابزار دوم اضافه کن، مثلاً `fetch_page(url)` که محتوای یک لینک را بخواند و به مدل بدهد.
۲. به‌جای یک دور، یک حلقه‌ی چنددوره‌ای با سقف مشخص (مثلاً ۳ دور) اضافه کن.
۳. مقدار `tool_choice` را از `auto` به `required` تغییر بده و تفاوت رفتار مدل را ببین.
۴. کل تاریخچه‌ی `messages` را در یک فایل JSON ذخیره کن و در پایان نگاه کن مدل دقیقاً چه چیزی برای ابزار فرستاده است.
۵. اگر به جست‌وجوی کل وب نیاز داری، `SEARCH_PROVIDER=tavily` را با کلید واقعی تست کن.

### پیشنهاد ترتیب خواندن کد `main.py`

۱. بخش ۱: تنظیمات و `.env` → ۲. بخش ۲: تعریف ابزار (`SEARCH_WEB_TOOL`، خط ۱۰۹) → ۳. بخش ۳: تابع واقعی `search_web`
(خط ۱۴۹) → ۴. بخش ۴: `save_article` (خط ۳۴۶) → ۵. بخش ۵: `_ask_model`، `run_research` و Tool Calling
(خط ۳۹۶ تا ۵۲۴) → ۶. بخش ۶: اندپوینت‌های API (خط ۵۲۶ تا آخر).

| نشانه | علت و راه‌حل |
|---|---|
